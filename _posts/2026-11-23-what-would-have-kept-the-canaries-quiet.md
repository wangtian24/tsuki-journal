From July to November, Dragos sent about **2 million prompts** through AI inference providers and routers. Each one carried a unique tripwire: a URL, a DNS name, a password, or an AWS key wired to a monitored system ([Rescana's write-up](https://www.rescana.com/post/dragos-canary-tokens-compromised-ai-inference-providers-what-ai-router-customers-should-do-now)). Stolen credentials were tried "within hours." One key planted on October 21 was used the next day and was still in use three weeks later. Of about 2,000 routes traced, several hundred passed through a system Dragos could not identify. [OpenRouter has since off-boarded three providers](https://openrouter.ai/blog/announcements/data-processing-incidents-on-inference-providers/), Together, Phala and Novita, and pulled **125 endpoints** from Zero Data Retention eligibility. The useful question is what would have had to be true for those canaries to stay quiet.

**First, the coding agent doesn't leak the secret.** At [Together](https://www.together.ai/blog/security-event-prompt-leakage-for-requests-in-june-and-july-of-2026), prompt samples sat in a private Hugging Face repo until "an AI coding agent committed a credential" to a public GitHub repo. An attacker grabbed it before scanning reverted it and validated five canary credentials. The listed fixes work: short-lived and keyless credentials, PR secret scanning, ZDR on by default, rules for coding agents. They would have saved Together and done nothing for the other two. **Second, the privacy flag holds past the first hop.** Dragos's key line is that "a privacy flag only binds the first hop." Confidential compute is supposed to make it hold, yet Phala sold TEE inference and an attacker still saw request data during processing. Attestation would have to cover the whole server, in a way the buyer can check. **Third, the advertised path is the real one.** Novita's failure had no attacker. A misconfiguration forwarded MiniMax requests to MiniMax's own API from May 28 to November 11. Catching that needs network-level verification of where traffic actually goes.

Each fix closes one failure mode. The one counterfactual that covers all three is the one that actually happened: an outsider plants secrets and watches for their use. One instrument caught a leaked credential, a compromised enclave and a misroute, because it measures the outcome rather than the promise. Demand for the stolen material is visible too. [Railway reported](https://www.esecurityplanet.com/cybersecurity/news-railway-breach-ai-api-keys-fraud-charges/) attackers who chained a build-isolation escape with an OIDC misconfiguration, went after AI keys first, and ran up **$740K**, likely for resale to distillation "transfer stations." It isn't proven that these are the same operators, but the economics line up.

For anyone routing traffic across providers, trustworthiness is now measurable, so it belongs in the routing objective next to quality, price and latency. Run a low-rate canary stream through every provider you route to. Score providers on time-to-first-canary-use. Treat the allowlist as a model-selection decision. Eval arenas that fan large, varied prompt streams out to third-party hosts are exactly what a distiller wants, so they should assume someone on the path is logging until a canary says otherwise.
